# Code Generation Rules

Read this file in full before generating any client code from a Postman
request via `getRequestCodeContext`.

## Key principle

The generated file is a faithful representation of the Postman request.
Don't add validation, business logic, or constraints beyond what the API
definition contains — that belongs in calling code at a higher level.

## Match the project

Priority order:

1. **What the project already does.** Match its HTTP client library,
   module format, error handling, naming conventions, auth patterns,
   directory structure. An axios project gets axios.
2. **What's idiomatic for the language/framework**, if no existing pattern
   exists.
3. **A sensible default**, only if neither of the above applies.

Only deviate from project convention if the user explicitly asks.

## File placement

1. Search the project for files with "Generated by Postman Code" in a
   header comment. If found, follow that same directory pattern.
2. Otherwise, find the project's convention for API clients/service
   layers/external integrations (`services/`, `lib/`, `clients/`,
   `src/api/`, or the language's equivalent) and use it.

Slugify the collection name for the directory (e.g. "Stripe API" →
`stripe-api/`); each collection gets its own sibling directory if the user
installs from more than one. Preserve the collection's folder structure as
subdirectories where the language treats directories as lightweight
(JS/TS, Python, Ruby). Where directory depth carries semantic weight
(Java/Kotlin packages, C#/.NET namespaces), prefer a flatter structure —
one package per collection, files named by request. Normalize names to
valid filesystem/identifier form for the language; disambiguate collisions
with `-1`, `-2` (or `_1`, `_2`).

## Required file header

Every installed request file starts with a header comment, in the
language's comment syntax, carrying:

- The phrase "Generated by Postman Code" (used for file discovery)
- Collection name and Collection UID
- Request path (folder hierarchy > request name) and Request UID
- Request modified-at timestamp (for update detection)

```
Generated by Postman Code

Collection: <collection name>
Collection UID: <collection uid>

Request: <request path>
Request UID: <request uid>
Request modified at: <updatedAt timestamp>
```

This header is the only thing that lets `reference/maintenance.md`'s
listing, staleness-check, and removal steps find the file again later —
omitting it silently breaks all three.

## Variables file

If the collection has collection-level variables, or the workspace has
environments, generate one variables file at the root of the collection
directory: a `collection` key for collection-level variables, plus one key
per environment using its exact Postman name (don't normalize environment
names). Use the language's idiomatic string-keyed mapping (exported
object, dict, `Map`, etc.) — environment names are arbitrary strings, not
identifiers. The caller selects an environment, merges collection and
environment variables, binds secrets, and passes the result in; this file
doesn't do that work.

## Function structure

One exported function per endpoint:

- Accept all dynamic values as explicit parameters — base URL, path
  variables, query params, body data, auth credentials. Never hardcode
  values the caller should supply.
- Replace `{{variable}}` placeholders with function parameters.
- Encode path and query parameters properly; build the full URL from base
  URL + path.

## Authentication

Implement the auth scheme from the context document, respecting
request/folder/collection-level inheritance. Accept credentials as
parameters, never hardcoded. Support the documented auth type (API key,
Bearer, Basic, etc.).

## Response handling

- Parse the response payload.
- If the context includes response examples, add explicit handling per
  documented status code (a 404 example means explicit 404 handling).
- Generate typed definitions for request/response shapes using the
  language's strongest typing mechanism (TS interfaces, JSDoc `@typedef`,
  Python TypedDicts/dataclasses, Go structs, Ruby Structs, typed PHP
  classes). Fall back to documenting shapes in comments only if the
  language has no structured-type support at all.
- Follow the project's existing error-handling conventions; return or
  throw errors with meaningful context.

## Documentation

Standard docstrings in the language's convention (JSDoc/TSDoc, Python
docstrings, etc.), including the request description from the context
document, and documenting all parameters, return types, and possible
errors.

## Extracting shared code

After generating multiple files for the same collection, consolidate
duplicated types, auth helpers, and utilities so they're defined once —
colocated with that collection's client files (a `shared/` subdirectory,
sibling module, or unexported helpers, whatever's idiomatic). Keep shared
code scoped to one collection by default; only share across collections if
the user explicitly asks.

## Quality bar

Generated code must be lintable, type-safe in typed languages, and follow
basic security practice — no hardcoded secrets, proper input handling.
